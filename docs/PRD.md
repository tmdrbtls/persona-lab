## 1. 문서의 적용 범위와 근거

이 문서는 두 원문을 개발·디자인·검증 팀이 공유할 수 있는 제품 요구사항으로 통합한 초안이다. 원문 속 작업 지시나 프롬프트는 제품 설계를 위한 참고 자료로만 해석했다. 원문 파일은 수정하지 않았다.

- **[원문]**: 두 문서에 명시된 방향·범위·일정. 실제로 구현 또는 검증됐다는 뜻은 아니다.
- **[제안]**: 원문에 없는 운영 규칙, 수용 기준, 상세 설계 또는 모순을 해소하기 위한 변경안. 팀 합의 전에는 승인된 요구사항이 아니다.
- **[결정 필요]**: 담당자와 결정 시점을 정했으나 아직 확정할 수 없는 항목.

이하 각 절의 원문 근거는 `개발 p.n`, `기획 p.n`으로 표시한다. 상세 입력 제한, 상태, 분모, 오류 처리와 수용 기준은 별도 표시가 없어도 **[제안]**이다. 원문의 39%, 4.1/5, 5분 등은 예시 또는 목표이며 실측 성과로 사용하지 않는다. 데이터셋 규모·라이선스, 경쟁사 기능, 외부 연구 수치 등은 이번 문서 작성에서 별도 검증하지 않았으며 제품의 검증된 사실로 재사용하지 않는다.

### 1.1 원문에서 우선 보완한 사항

| 쟁점 | 원문 내용 | 이 PRD의 처리 |
|---|---|---|
| 오차 방향 | AI 39%, Real 52%인데 AI가 13%p 낙관적이라고 표기 | `AI - Real = -13%p`. AI 완료율이 실측보다 낮은 예측으로 수정. 개발 p.2·6 |
| 예시 인원·비율 불일치 | 실제 완료 8/15명과 52%가 함께 등장 | 8/15는 53.3%. 모든 비율은 원시 인원에서 계산. 개발 p.6 |
| 척도 혼합 | Ask 4.1/5와 Act·Real 완료율 비교 | 평균 점수와 완료율을 직접 차감하지 않음. Ask 4·5점 비율로 의향·행동 격차를 별도 계산 |
| Ask와 Act의 우열 | Real이 어느 쪽 수치에 가까운지로 정확도 판단 | 서로 다른 측정 개념이므로 단순 근접만으로 우열을 주장하지 않음. 공통 결과 변수 검증은 후속 연구 |
| 오차의 재사용 | 한 번 측정한 오차로 다음 스터디의 실제 값을 제시 | 과거 관측 차이를 조건·표본과 함께 참고 정보로 표시. 자동 보정 예측값은 MVP 제외 |
| 같은 조건 | 같은 study_id이면 동일 조건으로 간주 | 프로토타입·과제·문항·노출 정책의 버전까지 고정 |
| 질문 범위 | Q1~Q6 공통 원칙과 참가자 화면 Q5·Q6가 혼재 | 질문별 대상·시점 정의. 화면 문항은 Act·Real 공통, 제품 설명 문항은 Ask 전용 |
| 무한 반복 방지 | 한 번 재방문해도 이탈 처리 | 정상적인 뒤로가기를 허용하고 반복 한도 종료는 시스템 종료로 분리 |
| 8개 이탈 이유 | MAX_TURNS·OTHER가 추가 등장 | 8개는 사용자 이유. MAX_TURNS는 실행 종료 원인, OTHER는 리뷰 전용 보조 라벨 |
| 실제 행동 수집 | Figma 임베드에서 클릭 경로 수집을 전제 | 자동 수집 가능성을 기술 검증. 불가능하면 통제된 재생 화면으로 전환하거나 수기 수집으로 명시 |
| 표본 규모 | 12~15명이 순위 검증에 충분하다고 단정 | 탐색적 검증의 모집 목표로 유지. 정확도 보장·통계적 충분성 주장에는 사용하지 않음 |

## 2. 제품 정의와 해결할 문제

**PersonaLab은 제품팀이 Figma 프로토타입의 어느 화면을 먼저 수정해야 하는지 판단하도록, 동일한 AI 패널의 의향과 행동을 기록하고 실제 참가자의 행동과 비교해 근거와 한계를 함께 보여주는 웹 서비스다.** [원문: 기획 p.1~6, 개발 p.1~4]

제품 설명에 대한 긍정적인 반응만으로는 가입 흐름의 장애물을 알기 어렵다. 실제 조사를 매번 반복하기 어려운 팀은 빠르게 가설을 좁힐 수단이 필요하다. PersonaLab은 AI 결과를 실제 사용자 조사에 앞선 가설 탐색과 수정 우선순위 선정에 사용한다.

### 2.1 목표

1. 제품 설명·프로토타입·과제를 입력하면 AI 100명의 Ask와 Act 결과를 얻는다.
2. 같은 페르소나의 의향과 행동이 어긋나는 사례를 추적한다.
3. 동일 조건의 실제 참가자 12~15명 데이터를 수집해 이탈 지점·이유와 완료율 차이를 비교한다.
4. 숫자마다 표본 수, 실행 버전, 측정 상태와 해석 한계를 함께 보여준다.
5. 프로토타입을 수정하고 같은 패널로 다시 실행해 수정 전후를 비교한다.

### 2.2 제품이 약속하지 않는 것

실제 시장 구매 전환율, 출시 성공 여부, 모든 한국 사용자의 대표성, 사용자 조사의 대체, 고정된 정확도, 시선·감정·망설임의 측정은 약속하지 않는다. MVP의 Act는 정의된 화면·선택지·연결을 사용하는 시뮬레이션이며, 실제 앱을 자유롭게 탐색하는 에이전트가 아니다. [원문: 기획 p.6·9·13, 개발 p.3·8·11]

## 3. 사용자와 주요 사용 시나리오

| 사용자 | 필요한 일 | 제품에서 얻어야 하는 결과 |
|---|---|---|
| 초기 제품팀 PM·기획자 | 개발 전 검증 가설과 수정 순서 결정 | 최다 이탈 화면, 이유, 실제 결과와의 차이 |
| UX·UI 디자이너 | 화면·단계를 바꾼 뒤 결과 비교 | 버전별 경로·완료율 변화, 동일 패널 비교 |
| 리서치 운영자 | 과제 설계, 참가자 초대, 데이터 품질 확인 | 초대·진행 현황, 수집 누락·제외 사유 |
| 실제 참가자 | 안내받은 과제 수행과 간단한 응답 | 로그인 없이 명확한 안내와 중단 가능한 참여 화면 |
| 분석 담당자 | 근거 추적, 벤치마크 평가 | 버전이 고정된 로그, 지표 정의, 평가 데이터 분리 |

타깃 소비자와 제품 사용자를 구분한다. 20대 대학생은 최초 시뮬레이션·검증 대상이며, 서비스를 조작하는 주요 사용자는 제품팀이다. [제안]

**대표 시나리오:** 일정 관리 앱 PM이 회원가입 프로토타입과 제품 설명을 등록한다. AI 100명에게 Ask와 Act를 각각 실행한다. 실제 참가자에게 같은 버전의 과제를 배포한다. 결과에서 학교·관심분야 입력 화면의 이탈을 확인하고 해당 입력을 가입 이후로 옮긴다. 새 버전으로 같은 패널을 재실행한다. 새 화면에는 새 AI 결과와 이전 버전의 실측 근거를 구분해 표시한다.

## 4. MVP 범위와 우선순위

P0는 핵심 흐름을 완성하기 위한 필수 범위, P1은 P0 안정화 후 추가, P2는 후속 확장이다. 기능 축소가 필요하면 18절의 기준으로 범위 변경을 기록한다.

| 우선순위 | 범위 | 출시 판단 |
|---|---|---|
| P0 | 스터디 생성·목록, 제품 정보, 프로토타입 연결·수동 입력 | 새 스터디를 실행 가능한 상태로 설정할 수 있음 |
| P0 | 과제·문항 버전 고정, AI 패널 100명 생성 | Ask·Act·Real의 비교 조건을 추적할 수 있음 |
| P0 | Ask·Act 실행, 진행률, 로그, 비용·반복 상한 | 성공·이탈·오류를 구분하고 종료할 수 있음 |
| P0 | 실제 참가자 초대·동의·과제 수행·응답 수집 | 실제 관측 경로를 재구성할 수 있음 |
| P0 | AI/Real 리포트, 의향·행동 격차, 실측 차이·근거 표시 | 원시 데이터와 집계가 일치함 |
| P0 [제안] | 소유권 검사, 버전별 결과 보존, 재실행·전후 비교 | 다른 사용자 접근과 결과 혼합 방지 |
| P0 [제안] | 벤치마크 데이터·평가 산출 파이프라인 | 별도 운영 도구여도 됨. 고객용 관리 UI는 필수 아님 |
| P1 | 세그먼트 탐색, 전체 Persona Explorer, 다운로드 | P0의 간단한 근거 상세 보기 위에 확장 |
| P2 | Figma 플러그인, 기업 자체 데이터, 협업 권한 세분화 | MVP 제외 |
| 제외 | 실제 웹·앱 자유 조작, 에뮬레이터, 파인튜닝, 음성·화면 녹화, 디자인 품질 평가, 결제·과금 | 별도 계획 수립 후 검토 |

원문 근거: 개발 p.3·7~8, 기획 p.13. 로그인·비교 버전·운영 파이프라인 구체화는 제안이다.

## 5. 핵심 객체와 상태

### 5.1 스터디 구성

하나의 Study는 제품 정보, 프로토타입, 과제, 문항, AI 패널, 실행 결과, 실제 참가자와 리포트를 묶는다. MVP에서는 스터디 버전당 주 과제 1개, 시작 화면 1개, 목표 화면 1개를 사용한다. 복수 과제는 스터디 복제로 분리한다. [원문: 개발 p.2, 단일 과제 제한은 제안]

### 5.2 버전 규칙 [제안]

- 최초 실행 또는 참가자 초대 전에 StudyVersion을 잠근다. 잠금은 제품·프로토타입·과제·문항·가격 노출 정책의 스냅샷을 생성한다.
- 잠긴 설정을 수정하면 새 버전을 만든다. 기존 실행과 참가자 세션은 이전 버전에 남는다.
- AI 패널은 별도로 버전 관리한다. 화면 수정 효과를 비교할 때 같은 panel_id와 동일 페르소나 속성을 재사용한다.
- 실행마다 모델 식별자, 프롬프트 버전, 샘플링 시드, 실행 설정을 기록한다. 동일 설정이 LLM의 동일 응답을 보장하지는 않는다.
- Ask 결과와 Act는 같은 프로필을 사용하되 대화 세션을 분리한다. Act에 Ask 답변을 넣어 행동을 유도하지 않는다.
- 새 버전의 AI 결과에 이전 버전의 Real 결과를 현재 실측으로 합산하지 않는다.

### 5.3 상태 모델 [제안]

| 객체 | 상태 | 전이 규칙 |
|---|---|---|
| Study | draft → active → archived | active 여부와 개별 Run 진행 상태는 분리 |
| StudyVersion | draft → locked | 잠긴 버전 수정은 새 draft 생성 |
| Run | queued → running → succeeded / partial / failed / cancelled | 터미널 상태에서 원본 결과 변경 금지 |
| AI 세션 | pending → running → completed / abandoned / system_stopped / failed | 사용자 이탈과 시스템 종료 별도 저장 |
| 실제 세션 | invited → consented → in_progress → completed / abandoned / incomplete / withdrawn | 브라우저 종료만으로 이탈 이유 추정 금지 |
| Invite | active → consumed / expired / revoked | 한 초대 토큰에 한 참가자 세션 |

Run의 succeeded는 실행 대상 모두 유효한 답변 또는 행동 종료 결과를 남긴 상태다. Act에서 전원이 과제를 완료했다는 뜻이 아니다. 일부 기술 오류가 있으면 partial로 표시한다.

## 6. 사용자 흐름과 화면 요구사항

Ask는 프로토타입 없이 먼저 실행할 수 있어야 한다. 원문의 일렬 단계 잠금은 모드별 준비 조건으로 조정한다. [제안; 원문 Ask 우선 개발: 개발 p.18]

| 화면 | 주요 요소 | 다음 단계·상태 처리 |
|---|---|---|
| Studies | 이름, 버전, 최근 실행, AI/Real 수집 상태, 새 스터디 | 빈 목록은 생성 안내. 본인 소유만 조회 |
| Product | 제품명, 설명, 기능 목록, 가격 구조·금액 | 필수값·중복 기능 검사, 저장 실패 시 입력 보존 |
| Prototype | 링크, 연결 결과, 화면·버튼·목적지, 수동 입력 | 권한 부족·미지원 요소·끊긴 연결을 구분 |
| Task & Questions | 시작·목표 화면, 과제, 문항, 노출 시점 | 도달 불가능 목표 차단. 참가자 화면 미리보기 |
| Panel | 타깃 조건, 데이터 출처, 생성 수, 분포 요약 | 생성 전후 분포와 데이터 부족 경고 |
| Run | 모드별 실행 가능 여부, 예상 호출 수, 진행률, 로그, 취소 | 완료·이탈·오류 수 분리. 새로고침 후 복구 |
| Invite | 초대 생성, 만료·회수, 참여·완료·중단 수 | 미동의자 제외. 중복 세션 집계 방지 |
| Participant | 안내·동의, 과제, 프로토타입, 중단, 종료 문항 | AI 결과 비노출. 진행 경로 자동 또는 명시적 수집 |
| Report | AI/Real 퍼널, 이탈 지점·이유, 격차, 관측 차이 | 데이터 없음·수집 중·부분 결과·비교 불가를 각각 표시 |
| 근거 상세 | 선택한 지표의 인원·분모, 버전, 원문 응답·경로 | P0 간단한 상세 패널. 전체 Explorer는 P1 |

원문 근거: 개발 p.4~8. 화면은 데스크톱 연구자 뷰와 휴대폰에서도 참여 가능한 참가자 뷰를 구분한다. 실제 비교 실험의 기기·화면 크기는 운영자가 고정하고 기록한다. [제안]

## 7. 기능 상세 요구사항과 수용 기준

### FR-01. 스터디 생성·보관 [P0]

**입력:** 스터디명 필수, 설명 선택. 이름 1~100자 제안. 생성 즉시 소유자와 draft 버전을 만든다.

**수용 기준:** 저장 후 목록에서 다시 열 수 있다. 타인의 ID를 전달해도 조회·수정할 수 없다. 보관된 스터디는 결과를 읽을 수 있으나 새 실행·초대를 막는다. 영구 삭제는 보관과 별도 기능으로 정의한다.

### FR-02. 제품 정보 [P0]

**입력:** 제품명, 설명, 기능 ID·이름·설명, 가격 유형(무료/유료/무료+유료), 통화, 결제 주기, 금액. 무료는 0원, 미정은 null로 구분한다. 초기 입력 제한은 설명 5,000자, 기능 1~20개로 제안한다.

**수용 기준:** 기능 선택 결과가 등록된 기능 ID만 참조한다. 공백 설명, 음수 가격, 중복 기능 ID를 저장하지 않는다. 가격 노출 정책에 따라 Q6 이전의 제품 정보에서 가격을 마스킹할 수 있다.

### FR-03. 프로토타입 연결·검증 [P0]

**입력:** Figma 링크. **출력:** 화면 ID·명칭·이미지 또는 설명, 요소 ID·라벨·영역·목적지, 연결 그래프, 지원 여부, 가져온 시점과 버전.

MVP 지원 후보는 클릭에 의한 화면 이동이다. 오버레이·조건 분기·복잡한 입력 검증·외부 이동 등은 지원 여부를 기술 검증에서 확정하고, 지원하지 않는 동작을 누락한 채 실행 가능으로 표시하지 않는다.

**수용 기준:** 시작 화면에서 목표 화면으로 도달 가능한지 확인한다. 같은 텍스트의 버튼이 여러 개 있어도 요소 ID로 구분한다. 접근 권한 부족, 잘못된 링크, 연결 없음, 미지원 동작을 서로 다른 오류로 보여준다. 원본 수정은 자동 반영하지 않고 다시 가져와 새 버전을 만든다.

### FR-04. 수동 프로토타입 입력 [P0]

Figma 연동 실패 시 화면 이미지·화면 설명·버튼 영역·요소 ID·목적지를 입력할 수 있다. 사람이 작성한 설명임을 저장한다. 버튼 이름과 연결만으로 동작하는 제한형 데이터는 사용할 수 있지만 시각적 사용성 검증으로 표현하지 않는다.

**수용 기준:** 끊긴 목적지, 화면 없는 버튼, 목표 미도달을 저장·실행 단계에서 검출한다. 모든 실제 참가자와 AI가 같은 수동 버전을 사용한다. 원본 Figma와 달라진 부분을 운영자가 확인한다.

### FR-05. 과제·문항 확정 [P0]

과제 문장, 시작·목표 화면, 질문 문구·보기·순서·응답 타입·노출 조건을 버전으로 저장한다. AI와 Real의 공통 문항은 같은 원본에서 렌더링한다.

**수용 기준:** 공통 문항 해시가 다르면 직접 비교를 차단한다. 과제에 없는 성공 조건을 사후 추가하지 않는다. 화면에 도달하는 것이 성공인지 입력 완료까지 필요한지 미리 명시한다. MVP에서는 목표 화면 도달을 기본 성공 조건으로 사용한다.

### FR-06. AI 패널 생성 [P0]

타깃 연령·소속·앱 이용·가격 민감도 조건을 받아 공개 분포를 반영한 페르소나 100개를 샘플링한다. 데이터 출처, 조사 시점, 변환·결합 방법, 변수별 분포, 시드를 기록한다. 직접 관측되지 않은 파생 변수는 추정이라고 표시한다.

**수용 기준:** 요청한 수만큼 고유 ID가 생성된다. 타깃에 맞지 않는 속성 조합은 제외 또는 경고한다. 필수 경제 변수가 없으면 가격 해석 제한을 표시한다. 패널 재생성은 이전 패널을 덮어쓰지 않는다. 동일 페르소나의 Ask·Act 연결이 유지된다.

데이터셋의 접근 가능성과 라이선스는 2주차에 확인한다. 불가하면 공개 조사 자료의 분포표로 대체하되, 출처가 확인되지 않은 수치를 임의로 채우지 않는다. [원문: 개발 p.9·19]

### FR-07. Ask 실행 [P0]

입력은 잠긴 제품·질문 버전과 AI 패널이다. 사용 의향 1~5, 필요·불필요 기능, 우려 카테고리, 자유 이유, 지불의향을 구조화해 저장한다. 화면을 보지 않는 Ask 문항은 화면 이해도 Q1과 별도 식별자로 관리한다.

**수용 기준:** 각 페르소나의 결과를 정확히 한 번 집계한다. 범위 밖 점수·없는 기능·잘못된 카테고리는 검증 실패로 처리한다. 응답 형식 재시도 후 실패하면 오류로 남기고 평균에 넣지 않는다. 100개 모두 처리되기 전에도 부분 결과와 처리 수를 볼 수 있다.

### FR-08. Act 실행 [P0]

입력은 잠긴 프로토타입·과제·공통 문항과 같은 AI 패널이다. 매 턴 현재 화면 설명, 사용 가능한 요소 목록, 이전 이동 이력만 제공한다. 목표 화면 ID나 정답 경로는 선택을 유도하는 관측 정보에 노출하지 않는다. 목표 판정은 서버가 한다.

**수용 기준:** 등록된 요소만 이동 대상으로 인정한다. 도착 화면을 기록한 후 성공 여부를 판정한다. 자발적 중단은 8개 이유 중 하나와 설명을 저장한다. 누적 경로로 마지막 화면과 종료 원인을 복원할 수 있다. 자유로운 브라우저 탐색이나 이미지 이해 성능을 구현한 것처럼 표시하지 않는다.

### FR-09. 실행 안전장치·비용 제한 [P0, 상세값 제안]

- 초기 스파이크는 20명·최대 3턴, 본 실행 기본 후보는 100명·최대 20회 유효 이동이다.
- 동일 화면의 세 번째 방문에서 반복 경고 후 시스템 중단하는 규칙을 초기 후보로 둔다. 한 번의 뒤로가기는 허용한다.
- 논리적 턴마다 형식·대상 검증 재시도는 최대 2회, 총 호출 시도는 최초 포함 3회다. 통신 재시도도 별도 무제한 루프 없이 총 시도 예산을 공유한다.
- 100명×20턴×3시도=최대 6,000회 Act 시도라는 상한 후보를 비용 검토에 사용한다. 실제 실행은 금액·토큰 예산 중 먼저 도달하는 한도에서도 멈춘다.
- MAX_TURNS, LOOP_LIMIT, BUDGET_LIMIT, PROVIDER_ERROR는 사용자 이탈 이유가 아니다.
- 취소 시 새 호출을 만들지 않고 이미 진행 중인 호출의 종료를 정리한다. 성공한 세션은 그대로 보존한다.

**수용 기준:** 반복 그래프·잘못된 JSON·API 실패에서도 유한 시간 안에 끝난다. 완료·중단된 페르소나를 추가 호출하지 않는다. 비용 초과 전에 다음 호출을 차단하고 사유를 보여준다. 금액 예산과 동시성은 5주차 측정 후 확정한다.

### FR-10. 실제 참가자 초대·동의 [P0]

운영자가 기본 15개의 개별 초대 링크를 생성한다. 참가자는 계정을 만들지 않고 목적·수집 항목·소요 시간·중단 방법을 확인한 뒤 동의한다. 토큰 만료 기본 7일, 한 토큰당 한 세션을 제안한다.

**수용 기준:** 미동의 상태에서 행동·응답 수집을 시작하지 않는다. 만료·회수 토큰은 참여할 수 없다. 새로고침은 같은 세션으로 복구하고 중복 참가자로 세지 않는다. 운영자에게 다른 참가자의 응답이 노출되지 않는 참가자 전용 화면을 제공한다.

### FR-11. 실제 행동·종료 응답 수집 [P0]

과제 안내 → 공통 시작 문항 → 프로토타입 조작 → 완료 또는 명시적 중단 → 종료 문항 순으로 제공한다. 클릭·화면 이동·중단 이벤트에 순번과 식별자를 부여한다. 실제 이름·학교명 등은 더미 입력 사용을 안내한다.

**수용 기준:** 유효한 이동은 경로와 일치한다. 중복 전송은 한 번만 저장한다. 저장 실패 시 재시도 상태를 알려준다. 탭 종료·장시간 미응답은 incomplete이며 특정 이탈 이유로 바꾸지 않는다. 목표 도달 후 설문 미응답이어도 행동 완료와 문항 결측을 분리한다.

자동 로그를 확보할 수 없는 경우 관찰자가 명시적으로 기록한 수기 데이터만 사용한다. `collection_method=manual`과 관찰자·수정 이력을 남긴다. 설문 답변으로 클릭 경로를 만들어내지 않는다.

### FR-12. 통합 리포트 [P0]

첫 화면에 최다 이탈 화면, 이유 상위 3개, AI/Real 퍼널, 실측 비교 상태를 배치한다. Ask 평균·긍정 비율, 의향·행동 격차, 실행 품질은 이어서 표시한다.

**수용 기준:** 모든 비율에 분자·분모를 확인할 수 있다. AI 문장은 `AI 생성 응답 · Synthetic User Response`, 실제 응답은 `실제 참가자 응답`으로 표시한다. Real이 없으면 0%가 아닌 ‘실측 데이터 없음’이다. 부분 실행 결과에는 품질 경고가 붙는다. 원시 로그 없는 시간·감정·시선 설명은 생성하지 않는다.

### FR-13. 수정·재실행·버전 비교 [P0, 제안]

기존 버전 복제 → 변경 내용 기록 → 새 버전 잠금 → 같은 패널로 Act 재실행 → 이전 실행과 비교 순서다. 비교 대상 Run은 사용자가 명시적으로 선택하며 임의의 실행을 유리한 결과로 자동 선택하지 않는다.

**수용 기준:** 변경하지 않은 모델·패널·문항 조건을 확인할 수 있다. 조건이 달라지면 복합 변경 경고를 표시한다. 새 Real 데이터가 없으면 ‘수정 후 AI 시뮬레이션 결과, 실제 재검증 없음’이라고 표시한다. 목표나 화면 구조 변경 시 화면 간 대응을 확인할 수 없으면 화면별 직접 비교를 제공하지 않는다.

### FR-14. 과거 실측 차이 표시 [P0, 자동 보정은 제외]

현재 스터디의 AI/Real 차이와 과거 스터디에서 관측된 차이를 구분한다. 과거 근거에는 대상, 과제 유형, 프로토타입 버전, 모델·문항 버전, 표본 수, 측정일, 출처 스터디를 포함한다.

**수용 기준:** 단일 실험을 ‘이 유형의 평균 오차’로 표현하지 않는다. 조건이 다른 근거는 자동 적용하지 않는다. 비교 가능 조건은 D3가 승인한 명시적 매칭 규칙으로 관리한다. 현재 실행의 오류 비율이 높으면 과거 차이를 병기하더라도 신뢰도를 높게 표시하지 않는다.

### FR-15. 근거 추적·세그먼트 [P0/P1]

P0는 리포트 수치를 클릭해 해당 인원·분모·경로·응답 원문을 확인하는 최소 상세 보기를 제공한다. 전체 패널 탐색, 가격 민감도 등 세그먼트 필터와 턴 JSON 탐색은 P1이다.

**수용 기준:** P023의 Ask와 Act가 다른 프로필과 연결되지 않는다. 소규모 세그먼트는 n을 표시하며 일반화하지 않는다. P1 필터는 분자와 분모에 함께 적용된다.

| Q3 | Act·Real, 매 화면 | 계속 진행 또는 그만두기 | 이동 또는 명시적 중단 이벤트 |
| Q4 | Act·Real, 명시적 중단 시 | 그만두는 가장 큰 이유 | 동일한 8개 보기, 보충 설명 선택 |
| Q5 | Ask 종료·Act/Real 종료 | 현재 서비스에서 옮길 이유가 있는가? 1~5 | 모드별 표시, 같은 개념끼리만 비교 |
| Q6 | Ask 종료·Act/Real 종료 | 월 최대 얼마까지 지불할 의향이 있는가? 원 단위 | 0원과 무응답 구분, 중앙값·분포 |

실제 참가자는 응답 거부 또는 ‘해당 없음’을 선택할 수 있다. AI는 해당 조건이 성립하지 않으면 null을 반환하고 이유를 기록한다. 결측을 0점·0원으로 바꾸지 않는다.

### 8.1 가격 노출

제품 입력 가격을 LLM에 이미 제공하고 Q6 문장만 바꾸는 것으로 앵커링이 사라졌다고 주장하지 않는다. `price_exposure=hidden_before_q6 / exposed`를 버전에 저장한다. 기본 실험안은 Q6 전에 숫자 가격을 숨기는 것이다. 프로토타입 화면에 가격이 있으면 가격 노출 조건으로 기록하고 AI·Real에 동일하게 적용한다. [제안]

### 8.2 공통 사용자 이탈 이유

| 코드 | 참가자 표시 문구 |
|---|---|
| UNCLEAR_PURPOSE | 무슨 앱인지 모르겠다 |
| TOO_MANY_STEPS | 단계나 입력 항목이 너무 많다 |
| PRIVACY | 개인정보를 과하게 요구한다 |
| PRICE | 가격이 부담된다 |
| TRUST | 믿기 어렵다 |
| FEATURE_MISSING | 필요한 기능이 없다 |
| SWITCHING_COST | 쓰던 것을 옮기기 번거롭다 |
| NAVIGATION_LOST | 어디로 가야 할지 모르겠다 |

6주차 말 카테고리 버전을 동결한다. 실제 참가자가 선택할 이유가 없다고 하면 응답을 강제하지 않고 null과 보충 설명을 저장한다. 해당 결측 비율은 별도로 보고한다. 리뷰의 OTHER와 실행 시스템 종료는 위 8개에 합산하지 않는다.

## 9. 지표 정의와 계산 규칙

이 절의 수식은 제품 구현 기준을 위한 제안이다. 개발 p.16의 지표를 유지하되 분모·동률·결측을 구체화했다.

### 9.1 공통 모집단

- `N_started`: 유효한 시작 이벤트가 있는 세션 수.
- `N_valid`: completed 또는 명시적 abandoned인 행동 세션 수.
- `N_technical`: 기술 오류·시스템 한도로 종료된 세션 수.
- `N_incomplete`: 실제 참가자의 미완료·연결 종료 등 결과 미확정 세션 수.
- `N_pair`: 같은 패널에서 유효 Ask와 유효 Act가 모두 있는 페르소나 수.

완료율의 기본 분모는 N_valid다. 단, 결과가 없는 세션을 제외해 성과가 높아 보이지 않도록 N_started, N_valid/N_started와 각 제외 사유를 반드시 함께 표시한다. 기술 실패가 시작 세션의 5%를 넘으면 품질 경고를 띄우는 안을 제안하며 임계값은 5주차에 확정한다. 수집 중인 Real 비교는 잠정 결과다.

### 9.2 지표 사전

| 지표 | 계산 | 예외·해석 |
|---|---|---|
| Ask 평균 의향 | 유효 A1 점수 합 / 유효 A1 응답 수 | 완료율과 직접 차감하지 않음 |
| Ask 긍정 비율 | A1이 4 또는 5인 수 / 유효 A1 수 ×100 | 임계값 4점은 제안, 버전 고정 |
| Act·Real 완료율 | 목표 도달 세션 수 / 각 N_valid ×100 | 기술 종료·미확정은 별도, n 필수 |
| 의향·행동 격차 | N_pair 안의 Ask 긍정 비율 - Act 완료율 | 단위 %p. 행동 예측 정확도와 다름 |
| 긍정 후 미완료 | N_pair 중 A1≥4이고 abandoned인 수 / N_pair 중 A1≥4인 수 | 기술 오류를 미완료 행동으로 세지 않음 |
| 화면 도달률 | 해당 화면에 한 번 이상 도달한 유효 세션 수 / N_valid | 재방문 중복 제거 |
| 화면 조건부 이탈률 | 해당 화면에서 abandoned인 수 / 해당 화면 도달 세션 수 | 분모 0이면 N/A |
| 이탈 이유 비율 | 해당 이유 응답 수 / 유효 이유가 있는 abandoned 수 | 이유 미응답 수를 병기 |
| 최다 이탈 화면 일치 | AI와 Real의 최다 이탈 화면 집합 비교 | 동일 단일 화면일 때 ‘일치’, 동률은 ‘부분 겹침/동률’ |
| 이유 Top-3 일치 | AI Top-3와 Real Top-3 교집합 크기 / 3 | 양측 유효 카테고리 3개 미만이면 N/A. 경계 동률은 코드순 보조 정렬 후 동률 표시 |
| 이탈률 순위 상관 | 공통 화면의 조건부 이탈률 간 Spearman 상관 | 공통 유효 화면 3개 미만 또는 상수 배열이면 N/A, 동률 평균순위 |
| 부호 있는 완료율 차이 | Act 완료율 - Real 완료율 | 양수: AI 높음, 음수: AI 낮음 |
| 절대 완료율 차이 | 위 차이의 절댓값 | 방향 정보와 함께 표시 |
| 제시 가격 일치율 | 노출된 기준 가격과 같은 Q6 수 / 유효 Q6 수 | 가격 비노출이면 N/A. 인과적 앵커링 증거라고 단정하지 않음 |
| 최빈 금액 집중률 | 가장 빈번한 Q6 금액의 빈도 / 유효 Q6 수 | 가격 비노출에서도 측정 가능 |
| 행동 다양성 | 이탈 화면별 분포와 정규화 엔트로피 | 화면 ID의 수치 분산은 사용하지 않음. 이탈 0명 또는 화면 1개이면 N/A |

분기형 그래프에서는 화면 나열을 그대로 단조 감소 퍼널이라고 부르지 않는다. 사전에 정의한 필수 단계가 있을 때만 단계 퍼널을 만들고, 그 외는 화면 도달·이동 그래프와 조건부 이탈률을 제공한다. 기존 ‘잔존율 감소 순서’는 경로 구조만으로 결정될 수 있어 위 이탈률 순위 비교로 구체화했다.

### 9.3 계산 검수 예시: 모두 가상 데이터

- AI 39/100 완료, Real 8/15 완료 → AI 39.0%, Real 53.3%, 차이 -14.3%p.
- 별도 비율 예시로 AI 39%, Real 52% → 차이 -13%p. AI가 실제보다 낮게 예측한 사례다.
- N_pair=100, Ask 긍정 76명, Act 완료 39명 → 집계 격차 +37%p.
- 위 수치만으로 ‘긍정한 사람 중 37명이 실패’라고 계산할 수 없다. 그 값은 개인별 교차표에서 직접 세어야 한다.
- AI 100명 중 완료 39, 명시적 이탈 56, 기술 오류 5라면 기본 완료율은 39/95=41.1%, 유효 결과 확보율은 95/100=95%다.

### 9.4 관측 차이 표시 문구 예시

> 이 스터디에서 AI 완료율은 39.0%(39/100), 실제 참가자 완료율은 53.3%(8/15)로, AI 결과가 14.3%p 낮았습니다. 소규모 탐색적 조사 결과이며 다른 사용자·과제에 그대로 적용할 수 없습니다.

> 이전 버전에서 관측한 차이: -14.3%p. 현재 버전의 실제 참가자 결과는 아직 없습니다. 이 차이는 참고 정보이며 현재 결과를 보정한 예측값이 아닙니다.

‘오차’, ‘평균 차이’, ‘신뢰구간’은 구분한다. 차이 수치 하나를 신뢰구간이라고 부르지 않는다. 통계적 구간 추정은 방법·가정·반복 실험 설계를 확정한 후 별도 구현한다.

## 10. 검증 계획과 성공 기준

### 10.1 제품 완성도와 연구 결과를 분리

제품 성공은 데이터를 수집·비교·추적할 수 있는가로 판단한다. AI와 Real이 비슷하게 나왔는지는 연구 결과이며 출시 조건을 통과시키려고 조정하지 않는다. 원문에 없는 ‘정확도 90%’ 같은 목표를 추가하지 않는다.

| 구분 | 목표·증거 | 기준 |
|---|---|---|
| 제품 핵심 흐름 | 스터디 생성부터 수정 후 비교까지 완료 | P0 수용 기준 통과 |
| AI 실행 | 같은 패널 100명 Ask·Act 처리 | 각 세션이 결과 또는 명시적 오류로 종료, 누락 없음 |
| 실제 조사 | 대학생 12~15명 확보·조사 | 초대·시작·유효·완료 인원을 구분해 보고 |
| 데이터 신뢰성 | 원시 로그와 리포트 일치 | 중복·결측·분모 검수 통과 |
| 반복 사용 [제안] | 내부 파일럿 스터디 3개에서 수정 후 재실행 | 결과의 유용성 의견과 수정 결정 기록, 시장 성과 주장 금지 |
| 연구 결과 | 대표 지표·완료율 차이·편향 지표 산출 | 불일치와 N/A를 포함한 전체 결과 보고 |

### 10.2 1차 검증: 앱 리뷰 벤치마크

[원문: 기획 p.10·13, 개발 p.14~16]

국내 앱 20개를 보정용 10개와 평가용 10개로 사전 분리한다. 앱당 최근 저평점 리뷰 최대 100건, 총 최대 2,000건을 대상으로 한다. 리뷰 조건은 별점 3점 이하이며, 수집일·정렬·언어·플랫폼·중복 제외 규칙을 고정한다. 출시 시점 제품 설명·기능 정보의 출처와 날짜를 보존한다.

리뷰 하나당 가장 강한 불만 1개를 라벨링하고 적합한 카테고리가 없으면 OTHER로 둔다. 다섯 라벨러가 같은 10건을 독립 분류한다. 초기 일치도 정의는 리뷰별 라벨러 쌍 10개 중 일치한 쌍의 비율을 구한 뒤 10건 평균으로 제안한다. 원문의 70% 기준을 통과한 뒤 본작업을 시작하며, 실패하면 기준을 수정하고 새로운 공통 샘플로 재확인한다.

보정은 calib 데이터만 사용한다. 평가 데이터 조회와 실행에는 역할·버전·감사 이력을 적용한다. group 컬럼만 두는 것으로 누수를 방지했다고 간주하지 않는다. 평가 결과를 본 뒤 튜닝했다면 다음 실험은 새 버전으로 기록하고 같은 데이터에 대한 성능을 독립 평가로 다시 주장하지 않는다.

이 검증은 불만 종류·순위만 평가한다. 최근 리뷰는 출시 당시 상태와 다를 수 있고 모델이 앱을 사전 학습했을 가능성도 있으므로, 출시 후 정보를 입력에서 뺐다는 이유만으로 완전한 사전 예측 실험이라고 표현하지 않는다. 앱명 마스킹 및 제공 정보 제한 여부도 기록한다. [제안]

### 10.3 2차 검증: 동일 과제의 실제 참가자

[원문: 기획 p.10~12, 개발 p.15]

8주차 모집을 시작하고 9~10주차에 1인당 약 10~15분 조사한다. AI 실행과 같은 버전·과제·시작/목표·문항·가격 노출 조건을 사용한다. 참가자 기기, 모집 경로, 조건 이탈, 운영자 개입, 제외 사유를 기록한다. 이미 프로토타입 제작에 참여한 사람은 주 평가 집단에서 분리한다. [제안]

대표 결과는 최다 이탈 화면, 이탈 이유 Top-3, 공통 화면 이탈률 순위 비교다. 완료율 차이는 참고 지표다. 조사 후 유리한 참가자만 제외하거나 예측에 맞게 라벨을 바꾸지 않는다. 12명 미만이면 부족한 표본 수를 그대로 표시하고 제한적 사례 관찰로 보고한다.

동일 문구를 사용해도 AI는 구조화된 설명을, 사람은 화면을 볼 수 있다. 이를 완전히 동일한 인지 조건이라고 주장하지 않는다. 입력·정보 차이를 실험 기록에 남기며 시각적 디자인 판단으로 확대 해석하지 않는다.

### 10.4 Ask·Act 연구 가설의 범위

MVP가 직접 확인하는 것은 ‘같은 프로필의 의향과 행동이 어떻게 다른가’와 ‘Act의 이탈 패턴이 Real과 얼마나 일치하는가’다. ‘Act가 Ask보다 실제 행동을 더 정확히 예측한다’는 강한 주장은 공통 결과 변수에 대한 별도 예측값, 독립 평가 데이터와 평가 함수를 갖춘 후 검증한다. 현재의 의향 점수를 임의로 완료 확률로 변환하지 않는다.

| calibration_records | source_version, ai_run, real_cohort, metric, values, denominators, gap, conditions | 근거 없는 새 결과 보정 금지 |
| audit_events | actor, action, entity, timestamp, reason | 버전 잠금·제외·수기 수정 추적 |

AI와 Real 행동 로그는 공통 스키마를 사용하되 `participant_type`과 수집 방법을 유지한다. 실제 참가자에게 AI run_id를 억지로 부여하지 않고, 비교 리포트가 AI 실행과 Real 코호트를 명시적으로 선택한다. `screen_id`는 프로토타입 버전 안에서 해석한다.

## 12. API 계약 요구사항

원문 엔드포인트를 유지하는 방향으로 정리했다. 버전 잠금·세션·취소·비교 API는 제안이다. 최종 경로는 구현 시 조정 가능하나 동작 계약은 유지한다. [원문: 개발 p.14]

| 작업 | API 예시 | 계약 |
|---|---|---|
| 생성·목록 | POST /studies, GET /studies | 소유자 자동 지정, 목록 페이지 처리 |
| 입력 저장 | POST /studies/{id}/product, /task, /questions | draft version_id 필수, 잠긴 버전 충돌 반환 |
| 프로토타입 | POST /studies/{id}/prototype, /prototype/manual | 검증 결과·미지원 요소 반환 |
| 버전 확정 | POST /studies/{id}/versions/{vid}/lock | 실행 가능한 모드와 config_hash 반환 |
| 패널 생성 | POST /studies/{id}/panel/generate | panel_id와 분포·출처·경고 반환 |
| AI 실행 | POST /studies/{id}/runs | mode, version_id, panel_id, idempotency_key. 비동기 접수 |
| 진행 확인 | GET /runs/{id}/status | 총수·대기·진행·완료·이탈·오류·비용 |
| 실행 취소 | POST /runs/{id}/cancel | 취소 요청 중과 취소 완료 구분 |
| 초대 | POST /studies/{id}/invites | version_id, count, 만료일. 링크 최초 생성 시만 노출 |
| 참가 진입 | GET /participate/{token} | 해당 버전 안내·과제만 반환, 연구자 데이터 미포함 |
| 동의·시작 | POST /participate/{token}/consent, /start | 동의 버전·세션 ID 저장 |
| 행동·응답 | POST /participate/{token}/logs, /answers | event_id·seq 중복 제거, 상태·경로 검증 |
| 종료·철회 | POST /participate/{token}/finish, /withdraw | 종료 원인과 문항 결측 분리, 재요청 안전 |

검증 오류는 필드별 사유, 권한 오류는 접근 불가, 상태 충돌은 잠금·중복 실행 사유, 외부 공급자 오류는 재시도 가능 여부를 포함한다. 진행률은 ‘처리 종료 세션/전체 대상’이며 과제 완료율과 구분한다. 진행 확인은 초기 2초 간격 폴링을 제안하고 백그라운드 탭에서는 간격을 늘린다.

## 13. 기술 의존성과 구현 검증

[원문: 기획 p.8] 기술 구성 후보는 React, FastAPI, PostgreSQL, Python 데이터 처리, 상용 LLM API, Figma 연동이다. 이 PRD는 특정 공급자 요금·기능이 현재 지원된다고 보증하지 않는다.

### 13.1 Figma 연동·실제 로그 수집 게이트

5주차 초까지 P2는 권한, 화면·연결·이미지 추출, 지원 상호작용, 실제 클릭 경로 수집 가능성을 함께 검증한다. 화면을 임베드할 수 있다는 사실만으로 내부 이벤트를 수집할 수 있다고 가정하지 않는다.

**A안:** 동일 버전의 Figma 재생과 검증된 이벤트 수집으로 진행한다.

**B안 [제안]:** 화면 이미지와 클릭 영역으로 구성한 자체 재생 화면을 사용한다. AI와 사람 모두 동일한 연결 그래프를 사용하고, 원본과 재생 화면의 차이를 기록한다. ‘Figma 원본과 완전히 동일한 사용 경험’이라고 주장하지 않는다.

**C안 [축소]:** Figma 링크+설문+관찰자 수기 기록. 자동 클릭 수집 기능은 미완료로 표시한다. 관찰하지 못한 클릭은 결측으로 둔다.

스파이크 전까지는 A안을 구현 완료로 전제한 일정·홍보 문구를 확정하지 않는다. B안의 개발량이 큰 경우 지원 화면 수와 상호작용을 제한하고 P1 기능을 뒤로 미룬다.

| AT-06 | 정상 뒤로가기 및 A↔B 반복 | 정상 복귀 허용, 반복 한도는 시스템 종료로 분리 |
| AT-07 | 이벤트를 두 번 전송·새로고침 | 중복 집계 없이 같은 세션 복구 |
| AT-08 | 실제 참가자가 목표 도달 후 설문 생략 | 행동 완료, 문항 결측으로 각각 집계 |
| AT-09 | 실제 참가자가 탭 종료 | 미확정 세션, 이유 자동 생성 없음 |
| AT-10 | 잠긴 문항·프로토타입 수정 | 새 버전 생성, 기존 AI/Real 로그 불변 |
| AT-11 | AI 39/100, Real 8/15 입력 | 39.0%, 53.3%, -14.3%p로 표시 |
| AT-12 | Ask 긍정과 Act 완료의 집계만 입력 | 개인 교차표 없이 긍정 후 실패 인원을 추정하지 않음 |
| AT-13 | Real 없음·분모 0·순위 동률 | 데이터 없음/N/A/동률 표시, 0%·100% 일치로 치환하지 않음 |
| AT-14 | 기술 오류 5개 포함 실행 | 유효 분모·전체 시작 수·오류 수 모두 표시 |
| AT-15 | 새 버전 AI 결과에 이전 Real 존재 | 이전 근거 표시, 현재 Real로 합산·자동 보정 금지 |
| AT-16 | 평가용 데이터로 보정 시도 | 권한·작업 경로에서 차단 또는 독립 평가 자격 상실 기록 |
| AT-17 | 타 사용자 스터디·만료 참가 토큰 접근 | 데이터 비노출·접근 차단 |
| AT-18 | 예산 한도·취소·공급자 장애 | 새 호출 중단, 부분 결과·원인 보존 |
| AT-19 | 가격 비노출 Q6 | 제시 가격 일치율 N/A, 최빈 금액 집중률은 별도 계산 |
| AT-20 | 캐시로 시연 | 저장된 실행의 날짜·버전 표시, 실시간 실행 오인 방지 |

출시 승인에는 P0별 구현 상태, 위 시나리오의 통과 증거, 알려진 결함, 축소 범위, 미확정 지표를 함께 남긴다. 실제 참가자 데이터가 없거나 행동 수집을 검증하지 못했다면 혼합 검증 MVP의 완료를 선언하지 않는다.

## 부록 B. MVP 완료 정의

제품팀이 스터디를 만들고 AI 100명의 의향·행동을 실행하며, 같은 버전의 실제 참가자 행동을 수집하고, 화면별 장애물과 관측 차이를 근거까지 추적할 수 있어야 한다. 수정 후 재실행 결과는 이전 실측과 구분해야 한다. 실험 결과가 가설에 맞지 않아도 그대로 보고하고, 데이터가 없는 부분은 없는 상태로 남기는 것까지가 제품의 완료 조건이다.
