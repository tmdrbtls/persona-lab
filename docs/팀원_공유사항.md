# PersonaLab 팀원 공유사항

작성일: 2026년 9월 23일

## 1. 이 프로젝트는 무엇인가

PersonaLab은 새로운 앱을 만들기 전에 사람들이 어디에서 불편함을 느끼고 중간에 나가는지 미리 확인하는 서비스다.

예를 들어 대학생용 일정 관리 앱을 만든다고 가정하면 다음 내용을 확인한다.

- 제품 설명을 본 인공지능 사용자들이 이 앱을 쓰고 싶어 하는가?
- 인공지능 사용자들이 회원가입 화면을 끝까지 통과하는가?
- 실제 참가자들은 어느 화면에서 가장 많이 나가는가?
- 인공지능 결과와 실제 참가자 결과에는 어떤 차이가 있는가?
- 화면을 수정한 뒤 결과가 어떻게 달라지는가?

현재 처음 검증할 대상은 **한국 20대 대학생을 위한 앱의 회원가입 과정**이다.

## 2. 처음에 한 일

처음에는 `개발 계획서`와 `기획서` 두 문서를 바탕으로 제품 요구사항 정의서를 만들었다.

제품 요구사항 정의서는 보통 **PRD**라고 부른다. PRD는 `Product Requirements Document`의 줄임말이며, 우리말로는 **어떤 제품을 왜 만들고, 어떤 기능이 필요하며, 무엇을 만족해야 완료인지 정리한 문서**다.

두 원문에 서로 맞지 않는 숫자나 표현이 있어 다음과 같이 바로잡았다.

- 인공지능 완료율 39%, 실제 완료율 52%라면 차이는 `인공지능 - 실제 = -13%p`로 표시한다.
- 실제 완료가 15명 중 8명이면 52%가 아니라 53.3%다.
- 사용 의향 점수와 실제 완료율은 서로 다른 값이므로 직접 빼서 정확도라고 부르지 않는다.
- 인공지능 결과를 실제 사람의 결과처럼 표현하지 않는다.
- 기술 오류로 멈춘 경우와 사용자가 스스로 그만둔 경우를 구분한다.
- 한 번의 작은 조사 결과를 모든 사용자에게 적용할 수 있는 사실처럼 표현하지 않는다.

정리된 문서는 [`docs/PRD.md`](./PRD.md)에 있다.

## 3. PRD를 바탕으로 만든 웹사이트

PRD의 핵심 흐름을 눈으로 확인할 수 있는 웹사이트를 만들었다.

현재 들어 있는 주요 화면은 다음과 같다.

1. 홈 화면
   - 전체 스터디 수
   - 인공지능 실행 수
   - 실제 참가자 수
   - 최근 스터디 목록

2. 스터디 목록
   - 여러 조사 프로젝트의 상태와 참가자 수 확인
   - 이름으로 검색

3. 새 스터디 만들기
   - 제품 정보 입력
   - 화면 시안 연결
   - 참가자 과제와 질문 설정
   - 인공지능 사용자 조건 설정

4. 결과 리포트
   - 인공지능과 실제 참가자의 완료율 비교
   - 단계별 통과율 그래프
   - 사람들이 중간에 나간 이유
   - 사용 의향과 실제 행동의 차이
   - 조사 결과를 계산한 근거 확인

5. 참가자와 실행 기록 화면
   - 참가자의 진행 상태
   - 인공지능 실행 상태와 비용 예시

## 4. 현재 웹사이트는 어디까지 실제로 작동하는가

현재 상태는 **프론트엔드 시연판**이다.

프론트엔드는 사용자가 보는 화면과 버튼, 표, 그래프처럼 웹사이트 앞부분을 뜻한다. 현재 화면 이동, 검색, 탭 전환, 스터디 생성 과정과 결과 화면은 직접 눌러볼 수 있다.

그러나 현재 표시되는 숫자와 참가자 정보는 설명을 위한 예시 자료다. 아직 다음 기능은 연결되지 않았다.

- 실제 회원가입과 로그인
- 실제 자료 저장
- 실제 데이터베이스
- 실제 인공지능 실행
- 실제 참가자 초대 주소 생성
- 피그마 화면 자동 가져오기
- 실제 조사 결과 계산

이 기능들은 나중에 백엔드와 연결해야 한다.

백엔드는 화면 뒤에서 자료를 저장하고 불러오며, 로그인 확인과 계산, 인공지능 호출 등을 처리하는 부분이다.

따라서 현재 사이트는 완성된 상용 서비스가 아니라 **제품의 화면 구성과 사용 흐름을 확인하고 백엔드 개발자와 논의하기 위한 작동 가능한 시연판**이다.

## 5. 사용한 기술을 쉽게 설명하면

### 리액트

리액트는 화면을 작은 부품으로 나누어 만드는 도구다. 예를 들어 상단 메뉴, 옆 메뉴, 지표 카드, 결과 그래프를 각각 따로 만든 뒤 한 화면에 조립한다.

### 비트

프로젝트에서 사용하는 `Vite`(비트)는 개발 중 웹사이트를 빠르게 실행하고, 인터넷에 올릴 수 있는 파일로 묶어주는 도구다.

### 깃허브

깃허브는 코드와 변경 기록을 인터넷에 보관하는 장소다. 누가 무엇을 바꿨는지 확인하고 이전 상태와 비교할 수 있다.

### 버셀

버셀은 깃허브의 코드를 실제 인터넷 주소에서 볼 수 있도록 자동으로 배포하는 서비스다. 배포는 만든 웹사이트를 다른 사람이 접속할 수 있게 인터넷에 올리는 작업을 뜻한다.

## 6. 깃허브와 공개 주소 연결

현재 개인 깃허브 계정 `tmdrbtls`에 `persona-lab` 저장소를 만들었다.

- 깃허브 저장소: <https://github.com/tmdrbtls/persona-lab>
- 공개 웹사이트: <https://persona-lab-blue.vercel.app>

깃허브의 `main`에 새 코드를 올리면 버셀이 자동으로 다시 배포한다. `main`은 현재 공식 버전을 보관하는 기본 줄기라고 생각하면 된다.

따라서 공개 주소를 매번 새로 만들 필요는 없다. 코드를 올릴 때마다 같은 주소의 내용이 새 버전으로 바뀐다.

저장소는 처음에 비공개였지만 현재는 공개 상태다. 코드 안에서 공개되면 안 되는 비밀 번호나 인공지능 서비스 열쇠는 발견되지 않았다. 커밋 기록에는 작업자의 이름과 이메일이 남아 있으며, 이 부분은 공개해도 괜찮다고 결정했다.

## 7. 코드를 화면과 부품별로 나눈 작업

처음에는 거의 모든 화면 코드가 `main.jsx` 파일 하나에 들어 있었다. 기능이 늘어나면 수정하기 어려워지므로 다음과 같이 나눴다.

```text
src/
├─ main.jsx                 웹사이트를 시작하는 파일
├─ App.jsx                  전체 화면 이동 관리
├─ styles.css               기본 화면 모양
├─ theme.css                현재 색상과 디자인
├─ pages/                   화면별 파일
├─ components/              여러 화면에서 다시 쓰는 부품
│  ├─ layout/               상단 메뉴와 옆 메뉴
│  ├─ report/               결과 리포트 부품
│  └─ ui/                   버튼, 상태표시, 카드 등
└─ data/
   └─ demoData.js           현재 화면에 쓰는 예시 자료
```

이 구조는 나중에 백엔드와 연결할 수 있다. 백엔드 작업을 시작하면 다음 폴더가 추가될 수 있다.

```text
src/
├─ api/          백엔드와 자료를 주고받는 코드
├─ hooks/        화면에서 자료를 불러오고 관리하는 코드
├─ routes/       인터넷 주소에 따라 화면을 바꾸는 코드
├─ types/        주고받는 자료의 모양을 정리하는 코드
└─ validations/  입력값이 올바른지 확인하는 코드
```

파일이 많다고 무조건 더 완성된 서비스는 아니다. 현재 규모에 필요한 만큼 나누어져 있으며 실제 기능이 추가되면 파일도 자연스럽게 늘어난다.

## 8. 디자인을 정한 과정

처음 디자인을 바로 결정하지 않고 `getdesign.md`에서 세 가지 디자인 설명을 참고했다.

- Airtable 분위기
- Intercom 분위기
- Linear 분위기

각 디자인을 PersonaLab 화면에 적용하면 어떤 모습인지 홈 화면과 결과 리포트 이미지로 만들어 비교했다.

최종 방향은 다음과 같이 정했다.

- Airtable처럼 흰색과 연한 크림색을 사용해 전체 화면을 깔끔하게 구성한다.
- Intercom처럼 결과 그래프를 크고 쉽게 읽히게 배치한다.
- 색상이 너무 많아 눈이 피로하지 않도록 코랄색과 짙은 초록색을 중심으로 사용한다.
- 인공지능 결과는 코랄색, 실제 참가자 결과는 초록색으로 구분한다.
- 결과 리포트의 단계별 통과율 그래프를 화면 중앙에 넓게 배치한다.

현재 첫 화면에는 제품 소개와 최근 스터디가 보인다. 중앙의 큰 비교 그래프는 `대학생 일정 관리 앱`을 누른 뒤 `결과 리포트`에서 확인할 수 있다.

디자인 후보 파일과 미리보기는 현재 작업자 컴퓨터의 `design-references` 폴더에만 있다. 실제 서비스 코드와 섞이지 않도록 아직 깃허브에는 올리지 않았다.

## 9. 지금까지 사용한 깃 명령어

깃은 코드 변경 기록을 관리하는 도구다.

```bash
git status
```

현재 어떤 파일이 바뀌었는지 확인한다. 파일을 수정하지 않는 안전한 확인 명령어다.

```bash
git add .
```

현재 폴더의 변경사항을 다음 기록에 포함할 대상으로 올린다. 필요 없는 파일까지 들어갈 수 있으므로 팀 작업에서는 `git add 파일이름`처럼 필요한 파일만 선택하는 편이 안전하다.

```bash
git commit -m "수정 내용"
```

선택한 변경사항을 하나의 기록으로 저장한다. 따옴표 안에는 무엇을 바꿨는지 알아볼 수 있게 적는다.

```bash
git push
```

내 컴퓨터에 만든 기록을 깃허브로 올린다. 현재 프로젝트에서는 `main`으로 올리면 버셀이 자동으로 공개 사이트를 갱신한다.

작업 순서는 보통 다음과 같다.

```text
파일 수정 → 동작 확인 → git status → git add → git commit → git push → 공개 주소 확인
```

## 10. 팀원이 자신의 컴퓨터에서 실행하는 방법

먼저 깃허브 저장소를 자신의 컴퓨터로 내려받는다.

```bash
git clone https://github.com/tmdrbtls/persona-lab.git
cd persona-lab
npm install
npm run dev
```

- `git clone`: 깃허브 저장소를 컴퓨터에 복사한다.
- `cd persona-lab`: 복사된 프로젝트 폴더로 이동한다.
- `npm install`: 프로젝트 실행에 필요한 도구를 설치한다.
- `npm run dev`: 개발용 웹사이트를 실행한다.

명령어를 실행하면 터미널에 `http://localhost:숫자` 형태의 주소가 나온다. 그 주소를 인터넷 브라우저에서 열면 된다.

## 11. 둘이 함께 작업할 때 권장하는 방식

처음에는 같은 파일을 동시에 수정하지 않는 것이 좋다.

예를 들면 다음처럼 일을 나눌 수 있다.

- 한 사람: 홈 화면과 스터디 목록
- 다른 사람: 결과 리포트와 참가자 화면
- 한 사람: 화면 디자인
- 다른 사람: 백엔드에서 받을 자료 형식 정리

작업을 시작하기 전에는 최신 코드를 내려받는다.

```bash
git pull
```

`git pull`은 깃허브에 있는 최신 변경사항을 내 컴퓨터로 가져오는 명령어다.

작업을 끝낸 뒤에는 다음 순서로 올린다.

```bash
git status
git add 수정한파일
git commit -m "무엇을 수정했는지 설명"
git push
```

둘이 동시에 같은 파일의 같은 부분을 바꾸면 충돌이 생길 수 있다. 충돌은 컴퓨터가 어느 내용을 남겨야 할지 판단하지 못하는 상태다. 처음에는 작업할 화면을 미리 나누고, 한 사람이 올린 뒤 다른 사람이 `git pull`을 하는 방식이 이해하기 쉽다.

## 12. 공개 저장소에 올리면 안 되는 것

다음 정보는 깃허브에 올리면 안 된다.

- 비밀번호
- 인공지능 서비스 열쇠
- 데이터베이스 접속 정보
- 참가자의 이름, 전화번호, 이메일 등 개인정보
- `.env` 파일에 들어 있는 비밀 설정

`.env`는 컴퓨터마다 다른 비밀 설정값을 저장하는 파일이다. 나중에 백엔드 주소나 서비스 열쇠가 필요하면 `.env.example`에는 값의 이름만 적고 실제 값은 각자 따로 보관한다.

- 두 원문을 하나의 PRD로 정리
- 계산 오류와 조사 해석 범위 수정
- 리액트 기반 프론트엔드 시연판 구현
- 홈, 스터디 목록, 생성, 리포트, 참가자 화면 구현
- 데스크톱과 휴대폰 크기 대응
- 개인 깃허브 저장소 생성 및 공개 전환
- 깃허브와 버셀 자동 배포 연결
- 화면·부품별 코드 분리
- Airtable과 Intercom을 섞은 디자인 적용
- 최신 코드의 제작용 묶음 만들기 확인 완료

- 오류·로딩·자료 없음 상태 보완
- 자동 검사 코드 추가
- 실제 참가자를 대상으로 한 조사 운영

백엔드 연결 전에는 PRD의 `API 계약 요구사항`과 `데이터 요구사항`을 함께 보면서 화면에서 어떤 자료를 보내고 받아야 하는지 먼저 맞추는 것이 좋다.

## 15. 꼭 기억할 점

현재 화면이 실제 서비스처럼 보이더라도 숫자와 참가자 자료는 예시다. 현재 결과를 실제 조사 결과라고 발표하면 안 된다.

이 프로젝트의 다음 큰 단계는 **예시 자료를 실제 백엔드 자료로 바꾸는 것**이다. 화면을 처음부터 다시 만들 필요는 없고, 현재 `demoData.js`에서 가져오는 값을 백엔드에서 받아오도록 바꾸면 된다.
